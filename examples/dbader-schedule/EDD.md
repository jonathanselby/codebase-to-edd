# dbader/schedule — Engineering Design Document

> Real-world worked example generated by applying `codebase-to-edd` to the public repository `dbader/schedule` at commit `82a43db1b938d8fdf60103bd41f329e06c8d3651`.

## 1. Executive system description

`schedule` is a lightweight in-process Python scheduling library. Callers create `Job` objects through `Scheduler.every()` or the module-level `every()` shortcut, configure their recurrence through a fluent API, attach a callable with `Job.do()`, and then periodically invoke `run_pending()` from their own process.

The library does not provide a daemon, worker service or durable scheduler database. Scheduled jobs and their timing state live in Python objects in process memory. The caller owns the event loop and determines how often `run_pending()` is called.

`Scheduler.run_pending()` selects jobs whose `next_run` has arrived, sorts them, and runs them. `Job.run()` invokes the stored callable, records `last_run`, computes the next run, and can return `CancelJob` when an `until()` deadline is exceeded. Job registration computes the initial `next_run` and appends the job to the scheduler's in-memory list.

A material semantic point is explicit in the code and documentation: **missed jobs are not replayed**. If `run_pending()` is called infrequently, the library runs a due job once rather than catching up every missed interval.

## 5. Runtime flows

### Flow A — register a job

1. Caller invokes `schedule.every(interval)` or `Scheduler.every(interval)`.
2. A `Job` object is created with the interval and associated scheduler.
3. Fluent properties/methods set unit, weekday, fixed time, random upper interval, tags or deadline.
4. Caller invokes `.do(callable, *args, **kwargs)`.
5. `Job.do()` stores a `functools.partial`, computes `next_run`, checks that a scheduler exists, and appends the job to `scheduler.jobs`.
6. The registered job remains in process memory until cancelled, cleared, or process exit.

### Flow B — run pending jobs

1. Application calls `run_pending()`.
2. The default scheduler or explicit `Scheduler` filters jobs where `job.should_run` is true.
3. Due jobs are sorted by `next_run`.
4. Each job is passed to `_run_job()`.
5. `_run_job()` invokes `job.run()`.
6. `Job.run()` calls the stored callable, records `last_run`, and schedules the next execution.
7. If `Job.run()` returns `CancelJob`, the scheduler removes the job.

**Important semantic:** `run_pending()` intentionally does not execute every missed interval. A job that should have run many times since the previous poll runs once when next checked.

### Flow C — calculate next run

1. `_schedule_next_run()` validates the configured unit.
2. It chooses either the fixed interval or a random interval bounded by `interval` and `latest`.
3. It calculates in the configured timezone if one exists.
4. Weekly jobs move to the configured weekday; `.at()` jobs move to the requested time.
5. It advances by the interval until `next_run > now`.
6. Timezone offset changes are normalised, with specific handling for DST gaps.
7. For backwards compatibility, timezone-aware calculations are converted back to a naive local timestamp before storage in `self.next_run`.

The core library does not show retry, durable queueing, process supervision, distributed coordination or catch-up execution.

## 11. Security boundaries

This is an in-process library rather than a network service.

- It exposes no authentication or authorisation boundary itself.
- Scheduled callables execute with the privileges of the hosting Python process.
- Any secrets, files or network access used by a job are the caller application's responsibility.
- Timezone names are externally supplied strings when the caller chooses to expose them; the library passes them to `pytz.timezone()`.
- There is no process isolation between the scheduler and scheduled callables.

## 12. Operational behaviour

### Known

- scheduler state is in memory;
- caller owns the polling loop;
- missed intervals are not replayed;
- jobs execute synchronously in the thread calling `run_pending()` unless the caller's job implementation introduces concurrency;
- library logging exists for scheduler events;
- no built-in metrics, health check, tracing, durable store or worker process exists;
- the package declares no mandatory runtime dependencies; `pytz` is optional for timezone support.

### Inferred

- long-running or blocking jobs will delay later jobs in the same `run_pending()` call unless the caller deliberately offloads work.
- the library is best suited to lightweight in-process scheduling where losing schedule state on process exit is acceptable or reconstructed by application startup.

## 13. Known / inferred / unknown

### Known

- `Scheduler.jobs` is the primary schedule registry.
- `.do()` registers a job only after calculating its first `next_run`.
- `run_pending()` runs currently due jobs and intentionally does not catch up missed runs.
- `Job.run()` reschedules after execution.
- state is process-local and non-durable.

### Inferred

- synchronous callable execution means one slow job can delay subsequent due jobs in the same scheduler thread.
- restart recovery is expected to be handled by application code re-registering jobs.

### Unknown

- whether typical users run multiple scheduler instances in one process;
- how applications persist business state associated with jobs;
- what supervision/restart pattern most deployments use;
- whether user applications generally isolate exceptions from scheduled callables.

## 14. Open questions

1. Should the EDD for a library explicitly distinguish library guarantees from caller responsibilities? This example suggests yes.
2. Is synchronous execution a deliberate product boundary or merely a minimal core design?
3. What exception semantics should callers rely on when a scheduled callable fails?
4. For timezone jobs, what guarantees are expected across ambiguous DST transitions?
5. Would a maintainer describe process restart/re-registration as an explicit operating assumption?
