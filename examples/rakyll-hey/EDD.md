# rakyll/hey — Engineering Design Document

> Real-world worked example generated by applying `codebase-to-edd` to the public repository `rakyll/hey` at commit `5626f79b8698df6daf9b25799c9805c6acc96740`.

## 1. Executive system description

`hey` is a small Go command-line HTTP load generator. The CLI parses load-test and HTTP options, constructs a template `http.Request`, packages execution settings into `requester.Work`, and starts the run.

`requester.Work` owns the runtime. It creates a bounded results channel and stop channel, starts a reporting goroutine, creates one shared `http.Client`, launches `C` worker goroutines, clones and sends requests, captures per-request timing through `net/http/httptrace`, and streams results to the reporter. The reporter aggregates latency, status-code, size and error data and prints either a human-readable summary or CSV.

The system has no durable application state. Its meaningful state is process-local and exists for one benchmark run.

Two material implementation observations are worth calling out:

- **KNOWN:** worker allocation uses integer division (`N / C`) and explicitly ignores the remainder, so when `N` is not divisible by `C`, fewer than `N` requests are sent.
- **KNOWN:** the HTTP transport sets `TLSClientConfig.InsecureSkipVerify = true`, so TLS server certificates are not verified during benchmark requests.

## 5. Runtime flows

### Flow A — normal count-based benchmark

1. `main` parses CLI flags and validates `-n` and `-c`.
2. It builds headers, optional body, proxy configuration and an `http.Request`.
3. It creates `requester.Work` with request/count/concurrency/transport settings.
4. `Work.Run()` initialises channels, captures a start time and creates the reporter.
5. A reporter goroutine starts consuming `result` values.
6. `runWorkers()` creates a single configured `http.Transport` and shared `http.Client`.
7. It launches `C` goroutines; each runs `N / C` iterations.
8. Each iteration clones the request, attaches `httptrace`, performs the HTTP call, drains/closes the response body, and sends one `result` to the channel.
9. Once workers finish, `Finish()` closes the results channel and waits for the reporter.
10. The reporter computes aggregate statistics and renders output.

**Material edge case:** `runWorkers()` comments that it ignores `N % C`. Therefore total attempts equal `floor(N/C) * C`, not necessarily `N`.

### Flow B — duration or interrupt stop

1. `main` can start a timer goroutine for `-z`, and always installs an `os.Interrupt` signal handler.
2. Either trigger calls `Work.Stop()`.
3. `Stop()` writes one stop token per configured worker to `stopCh`.
4. Workers check `stopCh` between requests and exit when they receive a token.
5. An in-flight HTTP request is not cancelled by `Stop()`; it completes or hits the configured client timeout before the worker checks again.
6. Remaining results are aggregated and the report is finalised.

### Flow C — per-request measurement

1. `makeRequest()` clones the request and attaches `httptrace.ClientTrace` callbacks.
2. Trace callbacks capture DNS, connection, request-write, time-to-first-byte and response-read timings.
3. `http.Client.Do()` performs the request.
4. On success, the body is drained to `io.Discard` and closed so timing represents full response consumption and connection reuse remains possible.
5. A `result` containing timings, status, error and content length is published to the reporter.

## 10. Failure and recovery behaviour

| Failure | Detection | Behaviour | Recovery | Confidence |
|---|---|---|---|---|
| invalid CLI input | validation/parsing error | print usage/error and exit | user correction | KNOWN |
| request fails | `http.Client.Do` error | error stored in result; other requests continue | no per-request retry | KNOWN |
| request timeout | HTTP client timeout | recorded as request error | next benchmark request continues | KNOWN |
| interrupt/duration reached | stop trigger | workers stop between requests | graceful aggregation of completed results | KNOWN |
| all successful-result latency set empty | zero successful latencies | snapshot returns without histogram data; averages are computed before that guard | no explicit special recovery | KNOWN |
| `N % C != 0` | not treated as error | remainder requests are never allocated | none | KNOWN |
| Windows performance counter init fails | zero return from system API | panic | process terminates | KNOWN |

## 11. Security boundaries

- The target URL, headers, body, proxy and basic-auth credentials are user-controlled inputs.
- `http.Transport` explicitly uses `InsecureSkipVerify: true`. **KNOWN:** TLS certificate verification is disabled for HTTPS benchmark traffic.
- Basic authentication is assembled by the CLI into the outbound request. The repository does not provide a secret store or credential masking layer.
- The tool sends arbitrary user-supplied HTTP requests to arbitrary targets. Authorisation to test a target is outside the codebase and therefore **UNKNOWN**.
- No sandbox exists between the process and optional body files read from the local filesystem.

## 12. Operational behaviour

### Known

- concurrency is goroutine-based;
- one `http.Client`/transport is shared across workers;
- stop handling is cooperative between requests;
- response bodies are fully drained and closed;
- request timing uses `httptrace` plus a platform-specific monotonic-ish timing helper;
- output is terminal/stdout-oriented summary or CSV;
- there is no durable result store;
- no application metrics endpoint, health endpoint or tracing exporter is present.

### Inferred

- the design is optimised for a short-lived local benchmark process rather than a continuously operated service.

## 13. Known / inferred / unknown

### Known

- `main` constructs one `Work` and calls `Run()`.
- workers execute HTTP requests concurrently and stream results to one reporter.
- all benchmark state is in memory.
- worker allocation can under-run the requested `N` when `N` is not divisible by `C`.
- certificate verification is disabled in the benchmark transport.

### Inferred

- a shared transport is intended to support realistic connection reuse unless keepalive is disabled.
- the report is intended to be the terminal product of a run rather than an API consumed by another persistent component.

### Unknown

- whether the request-count remainder behaviour is intentional product semantics or technical debt;
- whether disabling TLS verification is a deliberate load-testing choice or an historical default;
- expected behaviour when every request fails;
- whether benchmark results are commonly persisted by wrappers or external automation.

## 14. Open questions

1. Should `N` represent an exact request count for all valid values of `N` and `C`?
2. Should TLS certificate verification be configurable rather than always disabled?
3. Should `Stop()` cancel requests already in flight?
4. What output is expected when there are zero successful responses?
5. Is custom output template input intentionally supported beyond the documented summary/CSV choices?
